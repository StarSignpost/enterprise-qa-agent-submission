# 项目复盘、学习总结与下一步

日期：2026-11-01。本文按用户要求由AI根据本次实际协作过程代拟，采用第一人称组织项目选择；不把AI操作写成个人手工经历。技术学习总结来自可复核工程事实，不代表用户已经独立掌握。个人工时与会话外经历未知，明确留待补充。

## 1. 范围判断

我选择先完成命令行核心，采用Python标准库、本地合成资料和一个真实模型服务，将时间用在“模型选择动作—工具执行—观察回传—模型再决定”这条链路。框架、界面或部署并不是本题核心验收点。项目代码与实际运行主要由AI承担，我负责给出约束、选择阶段及改进方案。

这种范围控制换来了较少依赖和便于检查的Trace，也意味着项目没有通用语义检索、生产Runtime或大样本可靠性证据。最终源码有70项离线通过和2项真实增量，旧六业务的完整真实样本属于词条前版本；我不能把它们合并成最终源码所有验收都通过。

## 2. 复盘主线：严格引用如何同时可核验、可被模型使用

从实际失败看，最值得重点复盘的工程问题是：原文已经取到，引用仍因读取句柄错误而不能完成。S0正常场景实际用了7次请求，模型两次猜测 `read_call_id` 被拒绝，最后failed，见[原始记录](../examples/real/deepseek-2026-11-01/smoke/)。这不是一个可以靠手工把答案改为30天就解决的问题。

AI定位到协议调用ID在模型正文里不够显式。修正是在实际读取结果中提供可信句柄，提示逐字复制，并在引用错误时只反馈本轮真实读取的句柄和区间；完整性校验保持严格。新增回归后，真实重跑4次请求完成，见[修复后报告](../examples/real/deepseek-2026-11-01/normal-fixed/test-report.json)。旧日志未改，修复由AI完成。

这一过程说明：验证器拒绝是有效保护，但错误反馈必须提供模型可以使用的事实。文档ID、版本、原文偏移和读取句柄各有职责，不能混为一个标识。片段逐字存在仍不等于语义支持，所以候选答案另做同模型支持复核；后者有帮助，也仍可能误判。

## 3. 测试也需要接受证据约束

上下文测试曾要求“差旅报销期限”首轮必须completed；原文却只笼统规定报销30天。模型保留适用范围缺口导致测试失败。AI没有为过测试补造差旅范围，而是修正过严断言：允许首轮如实澄清/未完成，将真实输出传到历史，追问材料仍严格检查D03。见[原失败](../examples/real/deepseek-2026-11-01/business/test-report.json)与[重跑](../examples/real/deepseek-2026-11-01/follow-up-fixed/test-report.json)。

我据此把验证目标限定为事实、引用、缺口、状态与合法动作，不要求自然语言逐字一致或唯一顺序。评估规则本身出错时，应说明依据与改动并保留失败，不能把调整断言包装成模型能力提高。

## 4. 一次可解释的小改进及其限度

AI提出补一个“报销时效→报销期限”词条，我选择了该方案；具体编辑、测试和运行由AI完成。固定工具查询的期限/材料文档分数从2/2变成6/2，说明区分度提高。

资料反事实保持问题不变，最终代码下仅把D02的15改为30：冲突资料读取双方后澄清，一致资料读取双方后回答30天，见[实际对照](../examples/improvements/synonym-001/comparison.json)。修改前后的冲突基线都为5次请求，三次模型查询都自行加入了“期限”。因此我能陈述的是局部检索改善和资料响应，而不是总体准确率提高、节约调用或通用理解能力提升。

这也是本项目的学习结论：代码增量对照与资料反事实需要分开。A0/A1固定资料比较代码；A1/B1固定代码比较资料。只有观察实际结果，才能判断哪种变化真的得到验证。

## 5. 复现步骤也是交付的一部分

我实际在个人目录运行过工具测试命令并反馈ModuleNotFoundError，项目测试并未加载。AI随后确认命令需要从项目目录执行，补上切目录步骤，并在项目目录验证22项通过。我的纠正后重跑尚未确认，不能写成个人已通过，见[用户记录](../examples/improvements/synonym-001/review-command-fix/user-attempt-01.json)。

这条反馈提示文档必须交代工作目录、依赖、运行模式和输出目录规则。命令在AI的工作目录中成功，并不代表用户复制单行就能运行。
