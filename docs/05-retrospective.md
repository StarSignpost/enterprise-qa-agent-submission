# 项目复盘、学习总结与下一步

日期：2026-11-01。

## 1. 范围判断

我选择先完成命令行核心，采用Python标准库、本地合成资料和一个真实模型服务，将重点放在“模型选择动作—工具执行—观察回传—模型再决定”这条链路。对这个项目来说，先把决策过程和证据做清楚，比增加界面或部署更有价值。

这种范围控制减少了依赖，也让Trace更容易检查。最终源码对应的离线测试有70项通过，词条改进保留了真实对照，六项业务真实复测全部通过，共保存8个运行包、41次模型请求。项目仍缺少通用语义检索和大样本可靠性验证，因此我把完成范围限定在可复现的核心链路。

## 2. 复盘主线：严格引用如何同时可核验、可被模型使用

从实际失败看，最值得重点复盘的工程问题是：原文已经取到，引用仍因读取句柄错误而不能完成。S0正常场景实际用了7次请求，模型两次猜测 `read_call_id` 被拒绝，最后failed，见[原始记录](../examples/real/deepseek-2026-11-01/smoke/)。这不是一个可以靠手工把答案改为30天就解决的问题。

问题出在协议调用ID对模型不够显式。修正是在实际读取结果中提供可信句柄，提示逐字复制，并在引用错误时只反馈本轮真实读取的句柄和区间；完整性校验保持严格。新增回归后，真实重跑4次请求完成，见[修复后报告](../examples/real/deepseek-2026-11-01/normal-fixed/test-report.json)。原始失败记录保留，便于比较修复前后的行为。

我从中学到，严格校验和可用反馈需要一起设计。验证器拒绝错误引用只是第一步，还要让模型拿到能够修正错误的信息。文档ID、版本、原文偏移和读取句柄各有职责，不能混为一个标识。另一个重要区别是：片段逐字存在，不等于它支持答案。项目因此增加了候选答案的支持复核，但同模型复核仍可能误判。

## 3. 测试也需要接受证据约束

上下文测试曾要求“差旅报销期限”首轮必须completed；原文却只笼统规定报销30天。模型保留适用范围缺口导致测试失败。这里需要调整的是过严断言：允许首轮如实澄清或返回未完成，将真实输出传到历史，追问材料仍严格检查D03。见[原失败](../examples/real/deepseek-2026-11-01/business/test-report.json)与[重跑](../examples/real/deepseek-2026-11-01/follow-up-fixed/test-report.json)。

我据此把验证目标限定为事实、引用、缺口、状态与合法动作，不要求自然语言逐字一致或唯一顺序。评估规则本身出错时，应说明依据与改动并保留失败，不能把调整断言包装成模型能力提高。

## 4. 一次可解释的小改进及其限度

我选择补一个“报销时效→报销期限”词条。这个改动范围小、理由明确，可以直接比较检索结果。固定工具查询的期限/材料文档分数从2/2变成6/2，说明该问法下的区分度提高。

资料反事实保持问题不变，最终代码下仅把D02的15改为30：冲突资料读取双方后澄清，一致资料读取双方后回答30天，见[实际对照](../examples/improvements/synonym-001/comparison.json)。修改前后的冲突基线都为5次请求，三次模型查询都自行加入了“期限”。因此我能陈述的是局部检索改善和资料响应，而不是总体准确率提高、节约调用或通用理解能力提升。

这让我更清楚地理解了两种验证的区别：A0/A1固定资料比较代码，检验词条改动；A1/B1固定代码比较资料，检验模型是否随证据改变行为。以后评估类似改进时，我会先明确控制变量，再决定结论能说到什么程度。

## 5. 复现步骤也是交付的一部分

我在个人目录运行工具测试命令时遇到了ModuleNotFoundError，项目测试没有加载。原因是命令依赖当前工作目录。运行说明随后补上切换项目目录的步骤，在项目目录执行的22项工具测试全部通过。首次失败与后续验证分别保留，见[首次反馈](../examples/improvements/synonym-001/review-command-fix/user-attempt-01.json)和[项目目录运行记录](../examples/improvements/synonym-001/review-command-fix/ai-run.json)。

这次经历让我意识到，复现步骤也是功能交付的一部分。文档需要写明工作目录、依赖、运行模式和输出目录规则，并从读者打开终端的第一步开始说明。
